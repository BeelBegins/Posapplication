**Release mechanics — CORRECTED 2026-07-16, previous version of this note was wrong.** Real releases are **not** built manually on the user's Windows machine — they're built and published automatically by GitHub Actions (`.github/workflows/build-release.yml`, "Build Desktop and Android Release"), triggered on **every push to `main`** (`on: push: branches: [main]`, no path filter, no tag requirement — `workflow_dispatch` also available for a manual re-run). The workflow: a `test` job (npm test) gates three parallel jobs — `windows` (windows-latest runner, `electron-builder --win nsis`, 3 retries), `android` (matrix over all 4 products — pos/restaurant/sales/shopping — `./gradlew assembleRelease bundleRelease` per product, signed with a release keystore restored from 4 GitHub Actions secrets: `ANDROID_KEYSTORE_BASE64`/`ANDROID_KEYSTORE_PASSWORD`/`ANDROID_KEY_ALIAS`/`ANDROID_KEY_PASSWORD`), and `web` (Shopping PWA zip) — then a final `publish` job downloads all artifacts and runs `scripts/publish-github-release.cjs --require-product-apks --require-web` to create one combined GitHub Release with all 6 assets (Windows `.exe`, 4 product `.apk`s, Shopping web `.zip`).

**This means pushing to `main` is never a no-consequence action** — it always triggers a full production release build+publish, unconditionally. `scripts/publish-github-release.cjs` keys the release off `package.json`'s version (`getOrCreateRelease` looks up by tag `v${version}`; if that tag already exists it replaces the existing release's assets in place rather than creating a new one) — so **always bump `package.json`'s version before a push that's meant to land on `main`**, or the push silently overwrites the current release's assets under the same version number. This was already true locally; it's now automatic and unconditional via CI, so the stakes of forgetting are higher.

`npm run release` (the local manual path — `electron-builder --win nsis --publish never` + `scripts/publish-github-release.cjs` run by hand) still cannot run from this Claude Code sandbox (Linux, no Wine, no `GH_TOKEN`/`.env`) — but that's no longer "the established release flow," it was only ever a fallback. The real flow, confirmed 2026-07-16: all real development happens in this sandbox; a push to `main` (from here or anywhere) is what actually builds and publishes the release, on GitHub's own runners, not the user's Windows machine.
